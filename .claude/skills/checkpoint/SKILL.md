# 检查点机制

本项目是接力式双人协作 + vibe 工作流：没有固定分工，谁有空谁推进。检查点是唯一的进度固化手段——一段工作结束后，把"代码现状 + 交接状态"打包成一个快照。没有检查点的工作等于没有发生：下一位接手的人（或下一次会话）只能通过 HANDOFF.md 和 git 历史来理解项目，他没读过这段对话。

## 两种粒度

| 模式 | 典型触发 | 动作 |
|------|----------|------|
| 完整检查点（默认） | "打个检查点"、"保存进度"、"收尾"、"今天到这里" | 更新 HANDOFF.md → git commit（代码 + 文档同一提交） |
| 轻量打点 | "轻量检查点"、"小提交"、"打个点"、"快速存一下" | 仅 git commit，不动 HANDOFF.md |

用户没明说粒度时用完整检查点。轻量打点用于小任务的中间快照；一段完整工作（一个功能、一次会话）结束时必须用完整检查点，否则交接状态会断档。

## 完整检查点流程

1. **盘点变更**：并行运行 `git status -sb` 与 `git diff`（含已暂存部分），弄清本次会话实际改了什么；`-sb` 顺带核对分支与远程的领先/落后。工作流文档可能落后于现实（远程配置、路径等），边界事实以命令输出为准。若无任何变更且 HANDOFF.md 无需更新，直接告诉用户无需打点，不要创建空提交。

2. **更新 HANDOFF.md**（位于项目根目录；不存在则用文末模板创建）：
   - 更新四个板块：**当前状态 / 进行中 / 已决策 / 下一步**，内容来自本次会话的实际工作。
   - "已决策"写决策 + 一句话理由。重大设计决策的正文必须落到 `Docs/DESIGN.md` 对应章节（项目铁律），HANDOFF.md 里只留索引——否则文档会分叉。
   - 始终写给"下一个接手的人"看：他不知道对话里发生了什么，只知道文档里写了什么。省略号、"如前所述"这类对话内引用一律不允许。
   - 控制在一屏内：过期内容直接删，不是留着备注。HANDOFF.md 是工作内存，不是编年史——历史在 git log 里。

3. **提交**：点名 `git add` 本次相关文件（不要 `git add -A`，避免裹挟无关文件），创建一个提交。HANDOFF.md 的更新与代码进同一个提交——文档与代码分离会导致"文档说 A 代码是 B"。提交信息遵循仓库现有风格（英文祈使句、说明 why），如 `Add GOAP tutorial doc for non-game-dev collaborators`。

4. **汇报**：2–4 行总结：提交了什么、HANDOFF.md 记了什么、建议的下一步；末行注明执行模型与路由表符合性（如"执行模型：glm-5.3-flash（符合 AGENT_COMMON §6 路由表）"，偏离需说明原因）——模型路由的执行情况必须可追溯。让用户能一眼确认快照是否符合预期。

## 轻量打点流程

1. `git status` + `git diff` 盘点变更。
2. 点名 add 相关文件并 commit，消息风格同上。
3. 一句话汇报提交内容。

## 边界

- **产生新提交后即 `git push`**（origin = github.com/bbbushi/LLM-GOAP_Project，私有仓库）。push 失败不阻塞本地检查点：如实告知失败原因，网络/权限恢复后补推。
- 检查点不做测试/编译验证（用户的明确选择）——但如果明知本次变更会破坏编译，先指出来并建议修复后再打点，不要默默提交已知坏状态。
- 永远不为打点而制造空提交或凑数的文档改动。
- 本技能目录（`.claude/skills/`）随仓库入库，协作者拉取后同样能用 /checkpoint——不要把它加进 .gitignore。

## HANDOFF.md 模板（首次创建时使用）

````markdown
# HANDOFF

> 接力交接文档：工作开始前先读这里，结束前（/checkpoint 时）更新这里。

## 当前状态
（项目处于哪个里程碑、整体健康度，一句话）

## 进行中
（未完成的任务；半成品代码的位置与已知问题）

## 已决策
（关键决策 + 一句话理由；重大设计决策正文在 Docs/DESIGN.md，此处只留索引）

## 下一步
（按优先级排列的建议，供下一位接手者参考）
````
