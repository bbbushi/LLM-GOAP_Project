# 项目设计文档：基于 LLM 规则生成与 GOAP 自主规划的智能模拟经营游戏

> 版本 v0.7 ｜ 2026-09-13 ｜ 实验性项目 · 双人接力协作 · 当前目标：最小可玩单元
>
> 本文档整合自项目概览与第一轮架构评审，作为后续开发与论文写作的基准文档。

---

## 一、项目定位（一句话）

**LLM 当导演定规则，GOAP 当居民做执行，玩家当观察者看演化。**

类《辐射避难所》风格的挂机模拟经营游戏。AI 不是开发工具，而是游戏的核心机制：上层由大语言模型担任"规则制定者"，低频生成宏观规则与 NPC 人格；下层由 GOAP（Goal-Oriented Action Planning）驱动每个 NPC 高频自主决策。玩家以有限干预的方式引导并观察一个 AI 自治小镇的长期演化。

**项目性质：实验性项目。** 不追求可玩性与成品完整度，玩法仅为 AI 机制的实验载体。对架构的核心要求是**充足的可扩展性**——它是一个可以持续验证新想法的实验平台，而非一款要发售的游戏（详见 4.5）。

**当前阶段的最终目标：交付一个最小可玩单元**——规模最小、但双层 AI 闭环完整、可运行可演示（范围定义与验收标准见第六节）。

## 二、核心玩法

> 注：玩法从简，本节描述的只是实验的默认载体场景，机制本身应当可替换。

### 2.1 玩家角色：观察者 + 引导者

- 玩家**不**事必躬亲：日常资源分配、人口调配、发展规划均由 AI 自主完成。
- 玩家**拥有**宏观干预权限：发布发展指令（如"优先发展农业"）、调整政策优先级、在危机时刻投放资源。
- 核心乐趣：观看一个 AI 驱动的小镇如何自行运转、演化、应对危机；干预行为本身构成一种"实验"。

### 2.2 核心循环

```
资源生产/消耗(电力·食物·水·材料)
        │
        ▼
建筑建造/升级 ◄──► NPC 生成与调配
        │
        ▼
世界状态变化 ──► 触发 LLM 层调整规则 ──► GOAP 层行为随之改变
```

## 三、双层 AI 架构（核心创新）

```
玩家(宏观指令)
      │
      ▼
┌─────────────────────────────┐
│  LLM 层"规则制定者"(低频)     │  每游戏日一次 + 事件驱动（新NPC/危机/玩家指令）
│  · 生成规则配置 JSON          │
│  · 生成每日世界脚本（天气等）  │
│  · 生成 NPC 人格/目标/背景    │
│  · 将玩家指令翻译为规则调整    │
└──────────────┬──────────────┘
               │  只写数据，永不直接修改状态
               ▼
┌─────────────────────────────┐
│  规则验证层(每次LLM输出必经)   │  Schema校验 → 沙盒模拟 → 应用或回退
└──────────────┬──────────────┘
               ▼
┌─────────────────────────────┐
│  GOAP 层"行动执行者"(高频)    │  每个NPC独立 A* 规划器
│  World State → Goal → Action │  环境变化时实时重规划
│  链搜索 → 执行 → 状态更新      │
└──────────────┬──────────────┘
               ▼
         小镇演化 → 反馈至 LLM 层
```

### 3.1 职责对比

| | LLM 规则制定者 | GOAP 行动执行者 |
|---|---|---|
| **职责** | 制定宏观规则、生成 NPC | 执行具体行动、实时规划 |
| **调用频率** | 低频（每游戏日 + 事件驱动） | 高频（每 tick） |
| **输出形态** | 结构化 JSON 配置 | 状态变更与行动序列 |
| **优势** | 创造力、灵活性 | 可靠性、实时性、无幻觉 |

### 3.2 职责边界（铁律）

1. **LLM 只产出结构化数据**（目标定义、行动成本权重、NPC 性格参数），**永不直接修改游戏状态，永不生成代码**。
2. **GOAP 引擎是唯一的状态修改者**。所有规则先经规则验证层，通过后才注入引擎。
3. LLM 调用只发生在**游戏日边界或事件触发时**，**不在帧循环中同步等待 API**；API 失败/超时一律回退内置默认（规则回默认规则集，天气回随机天气表）。

### 3.3 GOAP 核心概念

- **World State**：世界的量化描述（食物份数、居民数、电量等）的键值对。
- **Action**：含前提条件（如"有斧头"）与执行效果（如"+木材"）。
- **Goal**：期望达成的状态（如"拥有 5 份木材"）。
- **Planner**：用 A* 从当前状态搜索成本最低的行动链。
- NPC 具备动态重规划能力，但严格遵循 LLM 设定的规则，保证行为可预测、可调试。

## 四、技术架构

### 4.1 技术栈

| 层级 | 选型 | 说明 |
|---|---|---|
| 游戏引擎 | **Unity (C#)** | 团队实际环境；C# GOAP 参考实现成熟；LLM API 仅为 HTTP 调用 |
| AI 推理 | DeepSeek / 通义千问 API | 成本低、中文支持好、无需本地部署 |
| GOAP 核心 | 自主实现 | 预估 500–800 行 C#，附单元测试 |
| 数据持久化 | JSON（规则/NPC配置） + 存档序列化 | 规则与 NPC 配置必须是可读 JSON，便于调试与研究分析 |
| 表现层 UI | **UI Toolkit**（UXML/USS，可纯 C# 构建） | 观测面板型 UI 的设计目标场景；纯文本资产可 diff、可 AI 生成，契合接力协作（理由与兜底见 §4.3） |

### 4.2 系统模块

1. **模拟内核**（headless）：World State、资源结算、GOAP Planner/Action/Goal，可脱离渲染独立运行与测试。
2. **规则验证层**：Schema 校验 → 沙盒模拟 N tick（目标可达性/资源守恒）→ 应用或回退。
3. **LLM 交互模块**：API 封装、Prompt 工程、JSON 解析、请求/响应日志与缓存。
4. **NPC Agent 模块**：每个 NPC 持有独立规划器、属性与记忆流。
5. **表现层**（Unity）：小镇可视化、NPC 行为日志、AI 决策依据面板。
6. **玩家干预模块**：宏观指令输入 → 传递给 LLM 层。

### 4.3 关键设计决策

- **规则验证层**（最大风险点的对策）：LLM 输出必须经 `JSON Schema 校验 → 沙盒模拟 N tick 验证可达性 → 通过才应用，失败回退默认规则集`。该层同时是研究点①的实验对象。
- **可复现性**：固定随机种子；记录并缓存全部 LLM 请求/响应（同一输入重放而非重调）。无此则对照实验无法控制变量。
- **NPC 记忆**：LLM 生成初始人格后，记忆 = 游戏内真实事件的结构化时间流；定期（低频）由 LLM 摘要压缩（摘要产物为结构化 JSON 记忆条目，不以自由文本回流，符合铁律 1），保证长期连贯性。
- **每日世界脚本（Day Script）**：LLM 每游戏日输出一份结构化日脚本（当前仅天气：类型 + 效果参数）。天气只通过**预定义效果通道**生效（生产倍率、消耗倍率、行动成本权重），不直接改状态，同样经规则验证层裁决；API 失败回退内置随机天气表。可一次生成多天、用完再续以降低调用频次。
- **成本控制**：NPC 批量生成（一次生成一批）；响应缓存；仅低频调用。
- **UI 选型：UI Toolkit 而非 UGUI**（2026-09-09）：本项目 UI 全部是可观测性面板（行为日志、资源曲线、决策依据、指令输入），UI Toolkit（保留模式、ListView 虚拟化、无 Canvas Rebuild）正是该场景的设计目标；UXML/USS 为纯文本资产，可 diff/review、可由 AI agent 可靠生成，契合接力协作（UGUI prefab 对编辑器外修改与 AI 生成不可靠）。**UGUI 仅在 Toolkit 无法覆盖处（如世界空间 UI）局部引入，两者可共存。** 已知代价：资源曲线需自制（`MeshGenerationContext` 画折线，约几十行）；NPC 头顶标签用 `WorldToScreenPoint` 投影到 overlay 实现。

### 4.4 协作模式：接力式开发

两人空闲时间都不固定，因此**不设固定角色与固定分工**——谁有空谁推进，另一人可随时接手任意模块继续干。接手成本低的前提是：**知识都沉淀在仓库里，而不是某个人的脑子里**。

为此约定五条机制：

1. **接口契约稳定，而非人员稳定**：World State 等模块间接口 Schema 一经冻结不再随意变动，任何人在任何模块上工作都围绕同一契约，接手时不需要重新对齐。
2. **任务卡粒度小**：所有工作拆成可独立完成、有明确"完成定义"的任务（如"实现 Planner 的 A* 搜索并附单测"），随时认领，做完即交接，不存在"做了一半只有自己懂"的长期状态。
3. **交接文档持续更新**：维护一份 `HANDOFF.md`，记录"当前进行到哪、为什么这么做、下一步是什么"。每次结束工作前花几分钟更新，接手者从文档恢复上下文，而非靠口口相传。
4. **重大决策落文档**：架构变更、规则取舍写入本文档或专门的决策记录，避免"当时为什么这么做"随时间丢失。
5. **模块可独立运行与测试**：每个模块（内核/验证层/LLM/表现层）单独可测，接手任一模块不需要先理解全部代码。

**冻结契约登记**：契约语义的单一事实源在 `Docs/schemas/`（Schema）与 `Assets/script/Core/Contracts/`（接口），此处只登记版本与指针。修改任一冻结契约须升 version 并同步本表。

| 契约 | 版本 | 冻结日期 | 事实源 | 要点 |
|---|---|---|---|---|
| World State | v1 | 2026-09-09 | `Docs/schemas/world-state.schema.json` | 纯数值平面键值对；缺失键视为 0；NPC 键 `npc.<id>.<key>`；天气不入世界状态；条件六算子（≥ 基线）、效果 Set/Add/MultiplyBy（+= 基线） |
| 核心接口 | v1 | 2026-09-09 | `Assets/script/Core/Contracts/` | `IAction / IGoal / IWorldState / IPlanner / IRuleProvider / ILLMProvider` + 伴生 `IRuleSet`（三类倍率通道）；内核 `noEngineReferences` |
| Action/Goal 配置 | v1 | 2026-09-13 | `Docs/schemas/action.schema.json`、`goal.schema.json` + 加载器 `Assets/script/Core/Config/` | 文件级集合格式 `{version, actions/goals:[…]}`；算子字符串与 `ConditionOp`/`EffectOp` 枚举名逐一对应，op 缺省取 ≥/+= 基线；id 库内唯一；加载器逐条镜像 Schema 约束（未知字段/算子显式报错，绝不静默忽略） |

### 4.5 可扩展性设计（一等要求）

项目定位为实验性项目，可玩性与完整度从简，**可扩展性是架构的第一验收标准**。具体落在五条设计原则：

1. **内容扩展靠数据，不靠代码**：Action、Goal、规则、NPC 人格、每日世界脚本全部是 JSON 配置。新增一种行为或天气类型 = 加一条配置（必要时新增一个原子 Action），Planner 等引擎代码不随内容增长。
2. **核心接口稳定，实现可替换**：`IAction / IGoal / IWorldState / IPlanner / IRuleProvider / ILLMProvider`（及伴生 `IRuleSet`）面向接口编程。规划算法、LLM 厂商（DeepSeek / 千问 / 本地模型）皆可替换对比——可替换性本身就是实验变量。
3. **模拟内核与表现层彻底解耦**：headless 内核是一等公民，Unity 界面、CLI 跑批、录像回放器都只是可插拔的前端。
4. **可观测性优先于可玩性**：事件总线 + 全量行为日志，每次规划、每次规则变更、每次 LLM 调用都留痕。实验项目的"完整性"体现在数据完备，而非界面完整。
5. **实验即配置**：随机种子、LLM 缓存、实验参数全部收敛到实验配置文件，对照组一键重跑（与 4.3 可复现性配合）。

## 五、研究定位（收敛后）

聚焦以下两个研究点，其余作为附加观察：

1. **LLM 规则生成的有效性**：何种 Prompt 策略能生成有效、平衡且多样的规则？由规则验证层的通过率/回退率量化。
2. **混合架构的可靠性**：LLM+GOAP 双层设计能否兼顾创造力与稳定性？

**实验设计**：多组小镇分别以不同规则策略（纯内置规则 / GOAP+LLM 规则 / 不同 Prompt 策略）运行相同 tick 数，比较存活率、资源增长曲线、危机恢复速度。依托可复现性设计（4.3）执行。

> 注：实验跑数安排在最小可玩单元交付之后的"实验框架"阶段（见 6.3），当前阶段仅做方法设计。

## 六、当前目标：最小可玩单元

当前阶段的**唯一最终目标**是交付一个最小可玩单元：规模最小，但双层 AI 闭环完整、可运行可演示。后续一切扩展（见 6.3）都建立在这个单元之上。

### 6.1 范围定义

**包含**（闭环所需的最小集合）：

- 1–3 个 NPC，各自运行 GOAP 规划器，围绕 2–3 种资源（如食物、电力）自主决策维持生存
- 完整双层闭环：资源危机检测 → LLM 生成一次规则调整 → 规则验证层裁决 → 注入后 NPC 行为发生可观察变化
- 玩家干预通道 ×1：一条宏观指令（如"优先发展农业"）能被 LLM 翻译为规则并生效
- 每日世界脚本（最小版）：LLM 每游戏日生成天气，经预定义效果通道影响生产/消耗，API 失败回退默认天气表
- 最小可视化：能看清每个 NPC 在做什么、资源曲线在怎么变（丑没关系）
- 全量行为日志：上述每个环节都留痕可查

**不包含**（明确砍掉，防止范围蔓延）：

- 建筑建造/升级系统、职业体系、昼夜与季节
- 天气以外的事件维度（访客、瘟疫、商人等）
- NPC 人格生成与记忆流（最小单元内 NPC 配置用手写 JSON；LLM 生成人格与记忆摘要归入 6.3 后续方向）
- 完整 UI、存档菜单、音效美术
- 实验框架与对照实验跑数（6.3）
- 多 LLM 厂商对比

### 6.2 验收标准（Definition of Done）

1. **自主运转**：运行后无任何干预，小镇自主运转 ≥ 3 游戏日不崩溃、NPC 不集体死亡
2. **LLM 闭环可追**：人为制造一次食物危机，日志可追完整链路——危机检测 → LLM 规则生成 → 验证层裁决 → NPC 行为改变
3. **干预生效**：玩家发出一条宏观指令，可观察到规则变化及其对 NPC 行为的影响
4. **可复现**：相同种子 + LLM 缓存下重跑结果一致
5. **每日世界脚本**：天气随游戏日由 LLM 更新，其影响可在日志与资源曲线中观察；断网/API 失败时回退默认天气表，游戏不中断

### 6.3 后续方向（交付后展开，当前不承诺）

- 规模化：更多 NPC、建筑系统、资源种类、职业体系
- NPC 人格的 LLM 生成与记忆流（最小单元内为手写 JSON 配置）
- 日脚本扩展：季节与昼夜、随机事件（访客、瘟疫、商人）等更多维度
- 实验框架：实验配置化、对照组一键跑批、数据分析脚本（论文素材在此阶段产出）
- 回放器与更完整的观察者工具
- 多 LLM 厂商/策略对比

### 6.4 里程碑

| 里程碑 | 预估 | 内容 | 对应验收 |
|---|---|---|---|
| **M1 GOAP 内核** | 2–3 周 | headless：1 NPC、3 Action、2 Goal 自主生存 24 游戏小时 + 单测；核心接口与 World State Schema 冻结，`HANDOFF.md` 建档 | 内容栏即验收（24 游戏小时 + 单测） |
| **M2 多 NPC 生存闭环** | 2–3 周 | 多 NPC 资源竞争/协作、危机检测、游戏日推进调度、事件总线 + 全量日志 | DoD-1 |
| **M3 LLM 规则闭环** | 2–4 周 | LLM 接入、Prompt 工程、规则验证层、危机触发规则调整、每日世界脚本（天气） | DoD-2、DoD-4、DoD-5 |
| **M4 最小可玩单元交付** | 1–2 周 | 最小可视化、玩家宏观指令通道、对照 DoD 逐项验收 | DoD-3、整体交付 |

**当前周期预估：约 2–3 个月。** 里程碑**内部**任务卡无强顺序，谁有空谁认领（符合接力协作模式）；跨里程碑存在软依赖——M3 的危机触发与每日世界脚本依赖 M2 的危机检测与游戏日调度，M4 依赖 M1–M3 整体交付——认领跨里程碑任务卡时先核对前置项。
