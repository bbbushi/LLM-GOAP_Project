- 执行模型：主会话 glm-5.3（调度与汇总，符合 §6 分档——对象含设计级文档）；三成员为独立子代理，其中合理性审查员自报运行于 glm-5.3-flash（子代理默认档），低于设计级审查档位，与 §6 分档存在偏差，风险已注明（本次其发现均为粒度较小的文档问题，未涉及深层架构权衡）

## 发现

### 硬伤（矛盾 / 违反约定）

**1. [矛盾] README「已知问题」称 manifest.json 仍含本机路径待处理，HANDOFF 已决策记录该问题已解决——两处对仓库现状的陈述互斥（事实核查支持 HANDOFF）**
- 位置：`README.md:54` ↔ `HANDOFF.md:18`
- 证据：README:「`Packages/manifest.json` 含 `file:D:/...` 形式的本机绝对路径（处理计划见 `HANDOFF.md`）……修复前可忽略或本地删改」；HANDOFF:「manifest.json 不再引用本机绝对路径……任何协作方 clone 后即可打开工程」。
- 说明：现行 `Packages/manifest.json` 已无任何 `file:` 引用，MCP 包（10.2.0）已实体入库 `Packages/com.coplaydev.unity-mcp/`。README 的「已知问题」为过期信息，其「处理计划见 HANDOFF」的指引也已失效。
- 建议：删除或改写 `README.md:54` 的「已知问题」段落，以 HANDOFF:18 与 manifest 现状为准。
- 来源：一致性审查员。

**2. [违反约定] World State 契约 v1 冻结这一重大设计决策未按约定落入 DESIGN.md，且 DESIGN.md 没有任何可承接契约登记/变更同步的章节（两名成员独立发现，互为印证）**
- 位置：`Docs/DESIGN.md`（全文无契约登记落点，§4.4 仅「一经冻结」原则）、`HANDOFF.md:17`（决策正文所在）、`Docs/schemas/world-state.schema.json:5`
- 证据：Schema 自我承诺「修改本契约须升 version 并**同步 Docs/DESIGN.md**」；AGENT_COMMON §8 要求「同步更新 `Docs/DESIGN.md` 版本号与对应章节」；但键命名空间（`npc.<id>.<key>`）、六种条件算子、Set/Add/MultiplyBy 效果算子、「天气不入世界状态」等契约要点在 DESIGN.md v0.5 中零落点，目前仅由 HANDOFF（工作内存）与 Schema description 承载。同板块内 UI 选型已按「正文进 DESIGN、HANDOFF 留索引」办理（HANDOFF:19），本条与之不一致。
- 说明：将来第一次改契约时，协作者不知道往 DESIGN.md 哪里写——要么漏同步、要么随手塞进不相干章节，正是防分叉机制要避免的。
- 建议：在 DESIGN.md §3.3 或 §4.4 新增「冻结契约登记」小节（契约名、版本、冻结日期、指向 `Docs/schemas/` 的指针，不复制契约全文），随后把 HANDOFF:17 契约决策压缩为一行索引。
- 来源：红线合规审计（定级「违反约定」）＋ 合理性审查员（独立发现同源问题，定级「建议」，汇总取高）。

### 存疑（待人判断）

**3. [存疑] 「里程碑之间无硬依赖顺序」与里程碑内容自相矛盾，可能误导协作者提前认领被阻塞的任务**
- 位置：`Docs/DESIGN.md:213`
- 证据：「里程碑之间无硬依赖顺序，符合接力协作模式」；而 M3 含「危机触发规则调整、每日世界脚本」（DESIGN:210）——危机触发依赖 M2 的危机检测、日脚本依赖 M2 的游戏日调度（`Docs/GOAP.md:108`：「游戏日调度在 M2 引入」）；M4 是对照 DoD 的整体交付，必然依赖 M1–M3。
- 说明：本意应是「里程碑内部任务卡可并行认领」，但字面读是「任意里程碑可先做」，与 M3/M4 内容直接冲突。
- 建议：改为「里程碑内部任务卡无强顺序；跨里程碑存在软依赖（M3 依赖 M2 的危机检测与游戏日调度），在任务卡上标注前置项」。
- 来源：合理性审查员。

**4. [存疑] NPC 人格生成与记忆流既不在最小单元「包含」清单、也未列入「不包含」清单，处于范围灰区**
- 位置：`Docs/DESIGN.md:115`、`:123`、`:55`、`:180-186`
- 证据：§4.2/§4.3 对人格生成与记忆摘要描述得相当具体（「每个 NPC 持有……记忆流」「定期由 LLM 摘要压缩」），但 §6.1 包含/不包含两份清单都未对其做范围裁决；里程碑旁证：M3 内容无人格/记忆项，说明实际计划是砍掉的，只是没写明。
- 说明：接力协作者读完 §4.2/§4.3 可能误认为记忆流是最小单元必做项。
- 建议：在 §6.1「不包含」中显式加一条「NPC 人格生成与记忆流（最小单元内由手写 JSON 配置代替，LLM 生成与摘要压缩归入 §6.3 后续实验）」。
- 来源：合理性审查员。

### 建议

**5. [不一致] 「核心接口」清单口径为六个，代码契约面实际另含第七个公共接口 `IRuleSet`，清单未覆盖**
- 位置：`Docs/DESIGN.md:145`、`Docs/AGENT_COMMON.md:32`、`HANDOFF.md:7`、`Assets/script/Core/Contracts/IRuleProvider.cs:12`
- 证据：三处文档均为「`IAction / IGoal / IWorldState / IPlanner / IRuleProvider / ILLMProvider`」；`IRuleProvider.cs` 内还定义并冻结了 `public interface IRuleSet`（三通道倍率字典），且 `IAction.cs`、`IPlanner.cs` 注释以 `<see cref="IRuleSet"/>` 引用。
- 说明：不构成互斥（清单未声称「仅此六个」），但「六接口=冻结契约面」的口径与代码现状已出现计数漂移。
- 建议：更新 DESIGN §4.5 与 AGENT_COMMON §4 时补入 `IRuleSet`（或加注「IRuleSet 随 IRuleProvider 一并冻结」），HANDOFF 措辞改「六核心接口 + IRuleSet」。
- 来源：一致性审查员（定级「建议」，因不构成互斥；汇总按其口径列于建议区首条）。

**6. [建议] M1 里程碑「对应验收」列为「—」，HANDOFF 以「M1 验收」指回该表时指针落空**

- 证据：M1 行验收列为「—」（验收内容实际写在同行内容栏）；HANDOFF 下一步④写「自主生存 24 游戏小时（M1 验收）」。
